# Review summary: evaluation scope proposal (27 November 2026)

Non-canonical. Summary of an external review report (Dutch original: *Beoordeling van propositie 0.6 van de EAI-standaard: evaluation scope in conformatieresultaten*), kept as provenance for the decisions recorded in the [proposal](README.md#decisions-27-november-2026). The original report is not stored in the repository.

- Reviewed: [`README.md`](README.md) in this directory, at commit `d176da1` (repository version 0.5.0-candidate).
- Verdict: **adopt, on three conditions.**

## What the review verified

The reviewer cloned the repository, ran `scripts/validate.py` and the reference validator (17 fixtures, 11 self-tests), and checked each factual claim in the proposal:

| Claim | Finding |
|---|---|
| Four of eleven example cases are machine-`conformant` while `non_conformant` is expected | Correct; cases and diagnostics as stated |
| 5 machine rules, the rest hybrid or human review | Correct: 5 machine, 31 hybrid, 2 human review (38 in total; about 87% outside a machine validator's scope) |
| The result schema cannot carry an evaluation scope | Correct: `additionalProperties: false`, `standard_version` fixed to `0.5.0-candidate` |
| `EAI-D034` is free | Correct; the highest existing code is `EAI-D033` |
| `related_rule: null` follows the pattern of `EAI-D015` and `EAI-D019` | Largely: those entries omit the field rather than set it to `null`; the schema allows both |
| The reference validator already reports scope in an extension | Correct, including a self-test |
| Validator contract steps 5 to 7; `EAI-R034` in the machine set | Correct |

## Strengths named

- Solves a real, verified interoperability problem with the smallest change: optional field, both existing result dimensions unchanged.
- The four rejected alternatives are argued convincingly.
- Builds on behaviour the reference validator already shows.
- Right timing: without a shared scope field, the 0.6 comparison of independent implementations is not fair, because a validator that decides fewer rules looks stricter rather than narrower.

## Weaknesses named

- Three open design questions (rule-to-profile scope, whether a profile may require the field, `EAI-D034`).
- Consumers validating against the 0.5 schema must update their schema copy; this needs active communication.
- An optional field only helps if validators fill it.

## Conditions and how they were handled

| Condition | Handling |
|---|---|
| 1. Decide the open points before canonisation | Decided on 27 November 2026; see [Decisions](README.md#decisions-27-november-2026) |
| 2. Correct the reference to the `EAI-D015`/`EAI-D019` pattern | Done: the `EAI-D034` entry now omits `related_rule`, and the text says the schema also allows `null` |
| 3. Communicate the consumer impact | Done: [Compatibility](README.md#compatibility) and [Migration and communication](README.md#migration-and-communication) list the release-note text, migration document and implementer guidance due at canonisation |

## After the review

An automated review of the follow-up pull request (E-AI-MODEL/EAI-standard#15) found that covering all rules needs a way to report rules that do not apply to the evaluated artifact. The proposal now adds the reason `not_applicable`. A second automated review noted that a rule can apply but fall outside the selected profile. Both questions are recorded as open point A, with two options for a maintainer decision.

## Follow-up named by the review

The remaining 0.6 work: a release-versioned conformance suite, a developer implementation guide, and above all a second, independent implementation to meet the 0.6 exit condition.
